# Дослідження UX форми створення тікета (UCU HESK)

**Завдання:** спростити процес заповнення форми — ідентифікувати незручності, запропонувати покращення, прототип.

---

## 1. Поточний потік (як зараз працює)

```
Головна (index.php)
    → "Створити тікет" (a=add)
    → [Якщо категорій > 1] Вибір категорії (category-select.php) — окрема сторінка
    → Форма тікета (create-ticket.php) — одна довга форма
    → submit_ticket.php → підтвердження
```

- **Вибір категорії:** або dropdown + кнопка "Продовжити", або список посилань (якщо категорій мало).
- **Форма тікета:** одна сторінка з усіма полями підряд: ім’я, email, підтвердження email, CC (опційно), пріоритет, кастомні поля (до/після повідомлення), тема, повідомлення, ще кастомні поля, вкладення, CAPTCHA, довгий текст "перед відправкою", кнопка "Відправити".

---

## 2. Що зараз незручно (ідентифіковані проблеми)

### 2.1 Зі стратегічного брифу (hesk-ucu-strategic-brief.html)

- **"Form UX is broken"** — форма характеризується як "half-working", додано новий крок, який веде на новий інстанс HESK (плутанина для студентів).
- **Планові напрямки:** "Fix form UX — remove broken step, simplify flow", "Structured intake forms per category", "Improved onboarding and form UX for students".

### 2.2 З коду та структури форми

| Проблема | Опис |
|----------|------|
| **Два кроки без контексту** | Спершу вибір категорії (окрема сторінка), потім форма. Користувач не бачить, навіщо категорія і що буде далі. |
| **Одна довга форма** | Всі поля на одній сторінці: контакти, пріоритет, кастомні поля, тема, повідомлення, вкладення, CAPTCHA. Довго, легко "загубитися" і пропустити обов’язкове поле. |
| **Різна кількість полів** | Залежно від категорії з’являються різні кастомні поля (до і після повідомлення). Користувач не знає заздалегідь, скільки всього треба заповнити. |
| **Немає пояснення категорій** | На екрані вибору категорії — тільки назви. Немає короткого опису "куди писати" (IT, аудиторії, адмін тощо). |
| **Повторення email** | Другий крок "Підтвердіть email" — додаткове поле без явної вигоди для користувача (особливо при майбутньому OAuth). |
| **CAPTCHA в кінці** | Користувач заповнює все, потім стикається з перевіркою. Помилка в CAPTCHA — можлива втрата частини введення при оновленні. |
| **Мало допомоги по ходу** | Є підказки KB під полем повідомлення (якщо увімкнено), але немає коротких підказок біля категорій і кастомних полів. |
| **Автозаповнення вимкнено** | `disable_autofill_customer` — зручність знижується для тих, хто без OAuth. |

### 2.3 Для контексту УКУ (студенти, орієнтація)

- Студенти не завжди знають, куди саме писати (категорія).
- Потрібна простота і передбачуваність: мінімум кроків, зрозумілі назви та описи.
- "Structured intake forms per category" — різні типи запитів (IT, кімнати, адмін) мають мати зрозумілу структуру, а не одну універсальну форму.

## 3. Як це покращити (напрямки)

### 3.1 Швидкі зміни (без зміни архітектури)

- **Опис категорій:** на екрані вибору категорії додати короткий текст під кожною категорією (наприклад: "Проблеми з комп’ютером, мережею, паролями").
- **Service message / банер:** на головній та на формі — один чіткий текст типу "Як подати заявку" і посилання на форму (згадано в брифі).
- **Прибрати "зламаний крок":** якщо є посилання або крок, що веде на старий/інший інстанс HESK — видалити або замінити на поточну форму.
- **Прогрес:** на формі тікета показати простий індикатор (наприклад: "Крок 2 з 2" або "Категорія обрана: IT підтримка").
- **Збереження чернетки:** зберігати введення в session при валідації; при помилці CAPTCHA не очищати форму.

### 3.2 Середні зміни (реструктуризація UX)

- **Об’єднати вибір категорії і початок форми:** одна сторінка: зверху вибір категорії (або великі картки з описом), одразу під нею — лише ті поля, що потрібні для обраної категорії (без перезавантаження сторінки, якщо це можливо через існуючу логіку).
- **Степове заповнення (wizard):**  
  - Крок 1: Категорія (+ опис).  
  - Крок 2: Контакти (ім’я, email; для залогінених — не показувати).  
  - Крок 3: Суть запиту (тема, повідомлення, кастомні поля саме для цієї категорії).  
  - Крок 4: Вкладення + CAPTCHA + відправка.  
  Це зменшує перевантаження і робить прогрес очевидним.
- **Спростити підтвердження email:** якщо планується OAuth — зробити підтвердження опційним або прибрати для залогінених; показувати одне поле email з підказкою "перевірте написання".

### 3.3 Довгостроково (згідно з брифом)

- **Structured intake forms per category:** окремі "сцени" або набори полів для типів запитів (IT, аудиторії, адмін тощо) з явними підказками і мінімумом зайвих полів.
- **Google OAuth на формі:** презаповнення імені та email, менше ручного введення і помилок.
- **Єдиний "авторитетний" крок для орієнтації:** один слайд/інструкція "як подати заявку" з посиланням на поточну форму (без зайвих кроків на інший інстанс).

## 4. Прототип (ідея для експерименту)

Нижче — опис прототипу, який можна реалізувати в HTML/CSS/JS окремо (наприклад, у `docs/prototypes/`), щоб "поекспериментувати і побавитись", без одразу змін у PHP.

### 4.1 Варіант A: Одна сторінка з категоріями та формою

- Верхня частина: **"Оберіть тип запиту"** — картки категорій (назва + 1 речення опису). При кліку картка вибирається, знизу з’являється форма.
- Форма показується одразу під обраною категорією, без переходу на іншу сторінку.
- Блоки форми згруповані: "Ваші контакти" → "Суть запиту" → "Вкладення (необов’язково)" → кнопка "Надіслати".
- Можливий міні-індикатор: "1. Категорія ✓ → 2. Контакти → 3. Запит".

### 4.2 Варіант B: Степовий wizard (3 кроки)

- **Крок 1:** тільки вибір категорії з короткими описами + кнопка "Далі".
- **Крок 2:** контакти (ім’я, email; при OAuth — "Увійти через Google" і потім не показувати).
- **Крок 3:** тема, повідомлення, кастомні поля для обраної категорії, вкладення, CAPTCHA, "Надіслати".
- Кнопки "Назад" / "Далі", на останньому кроці — "Назад" / "Надіслати".
- Збереження стану в JS (або в session при поступовій відправці на сервер), щоб при "Назад" дані не губились.

### 4.3 Що варто намалювати в Figma / на папері

1. **Екран вибору категорії:** картки з назвою + опис (1 рядок), можливо іконка.
2. **Один екран форми (скорочено):** групування блоків, видимий прогрес (наприклад, "Крок 2 з 3").
3. **Мобільний вигляд:** та сама логіка в одну колонку, великі кнопки категорій.

Якщо потрібен саме клікабельний прототип — можна зробити статичну HTML-сторінку з кількома "екранами" і перемиканням по кнопках (без бекенду), щоб перевірити відчуття потоку.

## 5. Що робити далі (чекліст для тебе)

- [ ] **Аудит "зламаного кроку":** знайти в конфігурації/коді/посиланнях місце, де додано крок на "новий інстанс HESK", і задокументувати або прибрати.
- [ ] **Додати описи категорій:** в адмінці категорій (якщо є поле опису) або в шаблоні `category-select.php` — виводити підказку під кожною категорією.
- [ ] **Зробити статичний прототип:** один HTML-файл (наприклад, wizard з 3 кроків) у `docs/prototypes/` або окремій гілці — подивитись на відгуки, потім переносити логіку в PHP/theme.
- [ ] **Поекспериментувати з групуванням полів:** на поточній формі додати візуальні роздільники (секції) і, за бажанням, "Крок 2 з 2" біля форми.
- [ ] **Перевірити збереження при помилці:** при невалідній CAPTCHA чи валідації — чи всі поля заповнені з session відновлюються (зараз частково є через `$_SESSION['c_*']`).

Якщо потрібно, можу запропонувати конкретні зміни в файлах (наприклад, `category-select.php` і `create-ticket.php`) або накидати один HTML-прототип wizard’а в репо.

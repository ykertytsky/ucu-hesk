01 — Current System State
Architecture

What HESK Actually Is

  • PHP monolith, no framework — full file-level control advantage
  • MySQL / MyISAM — no foreign keys, no transactions risk
  • Session-based auth — no tokens, no stateless API
  • Email integration via IMAP/POP3 + OAuth2 for Gmail/M365 solid
  • Inbound email → ticket via cron (5-min lag) bottleneck
  • Zero webhooks, zero event bus, zero async queue
  • Custom CSS/JS injection hooks in admin panel easy wins
  • File-based PHP cache for statuses, custom fields, KB
  • HTMLPurifier for input sanitization, TOTP MFA available
Management Intel — Confirmed Pain Points

What's Actually Broken

  • No Google SSO for users — #1 ticket loss vector. Wrong email = silent failure. No confirmation received. critical
  • No auto-routing from email — no tags, no category, no owner. Тетяна manually triages everything ops cost
  • Form UX is broken — "half-working," new step added pointing to new HESK instance
  • Orientation gap — students told to email directly, not use HESK. Inconsistent per faculty
  • Weekend SLA = none — staff Mon–Fri only, physical support by advance notice only
  • Low awareness — significant user base doesn't know helpdesk exists
Operational Constraints
Update Risk
HESK updates clobber custom code. Every file modification must be documented for post-update restoration. Minimal footprint changes preferred — "child theme" approach.
Security Gate
Cybersec specialist + sysadmin review before prod deploy. No formal process but gate is real. Sandbox-first, always. Ukrainian translation may "break" stock GitHub version — account for it locally.
Budget & Authority
Budget approved for paid HESK modules. Full tool replacement is on the table if justified with concrete advantages. Incremental delivery preferred over documentation-only output.

04 — Extension Concepts
Cluster A — Identity & Access (Root Cause Fix)
A-1
Google SSO on Submit Form
Patch submit_ticket.php to support OAuth2 PKCE flow via Google. On success, pre-fill verified email + name. No account required — just identity verification. Kills the #1 ticket loss vector cold.
effort: medium impact: critical code mod
A-2
Customer Accounts Enable
Customer account tables + code already in HESK — management confirmed it's built but unreleased publicly. Enable via settings, test in sandbox. Users get a ticket portal without re-entering email every time.
effort: low impact: high config
A-3
Email Verification Before Ticket Creation
On web form submit, send one-time verification link before creating ticket. Only creates after email confirmed. Eliminates "never got my ticket" from typo emails without requiring full OAuth2.
effort: low impact: high code mod
Cluster B — Smart Routing (Ops Efficiency)
B-1
Keyword-Based Auto-Category
Post-process inbound emails in the cron/IMAP fetch loop. Scan subject + body for keyword patterns mapped to category ID + owner. Pure PHP, zero external deps, zero latency added. 80% of cases follow predictable patterns.
effort: low impact: high cron mod
B-2
AI Email Classifier Sidecar
Separate Python/Node service reads HESK mailbox via IMAP, classifies email (LLM call), then forwards a tagged email back to HESK mailbox. HESK ingests it with category pre-set. Zero HESK code modification required.
effort: medium impact: high external service
B-3
Structured Intake Forms per Category
Replace generic form with category-specific flows (IT issue, room booking, admin request, library). Each maps to custom fields, pre-sets category + priority. Dramatically reduces Тетяна's manual triage burden.
effort: medium impact: high UX + code
Cluster C — Awareness & Adoption
C-1
Orientation Script Standardization
Non-technical but highest leverage. Standardize what every faculty tells students at orientation — one authoritative slide about HESK with QR code to submit form. Eliminates the "we weren't told" gap that Ірина surfaced.
effort: low impact: high ops / process
C-2
Email Footer Campaign
Add HESK submit link to IT department email signatures. When users reply to any IT email, they see "For future requests: [helpdesk link]". Persistent low-cost exposure — no campaigns needed.
effort: low impact: medium ops
C-3
HESK Embed Widget on Intranet
Floating "Need help?" button on the УКУ intranet/portal that opens HESK submit form inline or in new tab. Removes the "I don't know the URL" barrier. Inject via existing admin custom JS hook — no intranet code access needed.
effort: low impact: medium frontend
Cluster D — Intelligence Layer (Future State)
D-1
DB-Read Analytics Dashboard
Read-only MySQL connection from Metabase or Grafana. Bypasses the cloud statistics module paywall entirely. Volume by category, resolution time, staff load, busiest hours. Zero HESK code modification — just read the DB.
effort: medium impact: high external tool
D-2
AI Reply Suggestions Widget
Inject JS widget into admin reply form (via custom JS hook). Sends ticket context to external LLM API. Returns 2–3 draft reply suggestions. Staff picks or edits. Reduces reply time on common issues without any PHP modification.
effort: medium impact: medium JS injection
D-3
Escalation Cron
~50 lines of PHP cron script: find tickets open > N hours without staff reply, auto-notify owner + manager by email. Replicates the cloud-locked escalation module. Can also trigger Telegram or Slack webhook if needed.
effort: low impact: high cron + PHP
05 — Architecture Risks
MyISAM — acceptable but fragile. No foreign key enforcement, no transactions. Data integrity fully in PHP code. For simple CRUD extensions this is fine. For anything transactional (multi-step workflows, atomic state changes) — risk of silent corruption. Know when you're in that zone.
EAV antipattern in custom fields. custom1–custom100 are flat columns. Semantic field additions require schema migrations. Querying on custom field values at scale is ugly. Don't build anything requiring heavy custom field analytics.
No plugin architecture — every touch is a fork. No hooks, no observers. Extensions = direct file modification or parallel processes reading DB. Document every touched file: filename, lines changed, version, date, purpose. Updates will overwrite without this.
06 — Delivery Sequence
Incremental Delivery — Sandbox First, Security Review Before Prod
Sprint 1 — Zero-Code Wins (Week 1–2)
Enable customer accounts (A-2). Write KB article. Add service banner. Standardize orientation script (C-1). Audit broken form — document exactly what's broken and why. Deploy D-3 escalation cron.
Sprint 2 — Routing Triage (Week 3–4)
Implement keyword auto-category in IMAP cron (B-1). Sandbox test. Security review. Prod deploy. Measure Тетяна's manual routing time before/after — this is your first hard metric.
Sprint 3 — Identity Fix (Week 5–6)
Email verification hardening (A-3) — simplest auth improvement, no OAuth complexity. Evaluate Google SSO feasibility (A-1) based on УКУ's Google Workspace setup and security review feedback from Sprint 2.
Sprint 4 — Intelligence (Week 7–8)
Analytics via Metabase read-only (D-1). AI classifier sidecar POC (B-2). AI reply suggestions widget (D-2). Structured intake forms (B-3). Re-evaluate HESK replacement decision using real usage metrics.
On replacing HESK: Володимир is open but requires a detailed case with concrete advantages enumerated. The strongest argument comes after Sprint 1–2 data — if routing is still a disaster with keyword rules and customer accounts enabled, that's your evidence. Don't propose replacement before you have baseline metrics. Alternatives if needed: Zammad (open source, real REST API, OAuth2, good RBAC — closest drop-in), Freshdesk (hosted, Google SSO, routing rules native, costs money), Jira Service Management (if УКУ has Atlassian elsewhere).
